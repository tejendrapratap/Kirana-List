# Removing the setup

Today every family has to make a Google Sheet, paste Code.gs into Apps Script, deploy it, and paste a setup code on every phone. The goal is: install the app, tap Start or Join, type a name, done. Installing the app is part of the setup too, so distribution is covered below.

Researched on 2026-11-08, before 1.4 shipped. The release numbers in the migration plan are from then (1.4 became the quick wins and 1.5 the new name and look), and the code facts describe 1.3. Every price, free limit, policy and date the recommendation depends on (54 claims) was checked against official sources: 54 confirmed, 0 wrong, 0 unclear. See [Fact check](#fact-check). Change notifications were added to this plan on 2026-11-09, when they were taken out of 1.6 to wait for this move; that part reuses the checked claims and names what still has to be checked.

## Recommendation

Move to Firebase: Cloud Firestore (database in asia-south1, Mumbai) with anonymous Firebase Auth and a household invite code, on the free Spark plan. Users then do only two things: tap 'Start a new list' or 'Join a family list', and type their name. A second phone joins by scanning a QR code or pasting an 8-character code shared over WhatsApp. There is no Sheet, Apps Script, URL, token or Google sign-in. Design choices that keep the change safe for this codebase: 1) Keep the app's own SQLite mirror and outbox (GroceryDatabase, ListLogic, SyncWorker) and swap only the remote. Add a ListRemote interface behind SyncEngine, with FirestoreRemote as the new implementation, so offline behaviour, pending/failed-change UI and most tests stay. 2) Apply each outbox change in a Firestore transaction that copies Code.gs's rules: newest edit time wins (else 'stale'), deletes are tombstones (deleted=true) so an offline phone cannot bring an item back, Added At is written once, and a repeated change id counts as a duplicate. Transactions fail offline, which simply leaves the change in the outbox, as today. 3) Replace the 5-second poll with a foreground snapshot listener on items whose serverUpdatedAt is later than the last sync. Never listen to the whole list: a listener reattached after 30 minutes is billed like a new query. 4) Item document ID = a hash of the normalised name, because names can contain '/'. 5) Never enable anonymous auto clean-up. Add 'Leave this list and delete my data' and 'Export list' now. Add an optional 'Link Google account' (Credential Manager) before any public release, so a household whose last phone is reset can recover. Cost: $0 for your family. Roughly 200-400 households fit the free tier. Beyond that it costs about $0.003-0.004 per household per month at us-central1 prices (Mumbai prices not confirmed). Ruled out: InstantDB (shutting down); Realm/Atlas Device Sync (end of life); Appwrite Free and Couchbase free tier (inactivity pause or turn-off); Convex (no offline, free bandwidth fits about 10 households); ElectricSQL (no Kotlin client); PocketBase (pre-1.0, and you would run a VPS). One correction to the research notes: Code.gs's 'since' is an MD5 of the whole list (revisionOf_, line 2269). It returns 'unchanged' or the entire list, not per-row deltas, so no backend can simply reuse it as a delta API.

## Fallback

Cloudflare Worker + D1. Port the item rules of Code.gs (upsert/delete, tombstones, change-id dedupe, Added At, units) to a small Worker that keeps today's protocol-3 list/apply JSON. Add /households, /invites and /join, where joining returns a per-device secret that replaces the token. Store a per-household revision counter so unchanged polls cost one row read. The app keeps SheetsClient's OkHttp code, SyncEngine, LiveSync, GroceryDatabase and most tests almost unchanged, and users get the same zero-setup Start/Join flow. Switch to this if the Firestore transaction/rules design proves awkward, if you want low lock-in, or if you want to keep the sync engine you have already tested. Trade-offs: you write and run authentication, rate limiting, backups and abuse protection yourself; the data cannot be pinned to India; 'live' remains 5-second polling; and free caps fail hard until 00:00 UTC (05:30 IST). $5 a month covers about 600 households.

## Options compared

| Option | Verdict |
|---|---|
| 1. Firebase: Cloud Firestore + anonymous Firebase Auth + household invite code (free Spark plan, Mumbai region) | RECOMMENDED |
| 2. Your own small server: Cloudflare Worker + D1 (SQLite) speaking today's list/apply protocol | FALLBACK |
| 3. Google-native: the app signs in with Google, creates the Sheet itself and shares it (drive.file scope, no Apps Script) | NOT RECOMMENDED as the main path |
| 4. Supabase: Postgres + anonymous Auth + Realtime (Mumbai region) | THIRD CHOICE |

### 1. Firebase: Cloud Firestore + anonymous Firebase Auth + household invite code (free Spark plan, Mumbai region)

**What users do:** Phone A (starts the list): 1) Install the app. 2) The first screen offers 'Start a new list' or 'Join a family list'. Tap Start. 3) Type your name (e.g. 'Home') and tap Continue. The app signs in silently, with no Google account and no password, and creates the list in about a second. For your family only: this phone already has the Sheet set up, so the same screen offers 'Bring my items from the Google Sheet' (one tap; see migration plan). 4) Tap 'Add a phone'. The app shows a QR code and an 8-character code (e.g. K7QM-4XPD, valid 24-72 h), plus a 'Share on WhatsApp' button. Phone B: 1) Install the app. 2) Tap 'Join a family list'. 3) Scan the QR code with Google's code scanner (no camera-permission prompt), or paste the code from WhatsApp. 4) Type your name (e.g. 'Shop') and tap Join. The whole list appears. From then on, a change shows up on the other phone in about a second while the app is open, and edits made offline sync when the network is back. Nobody makes a Sheet, touches Apps Script, or pastes a URL or token, and no Google sign-in is needed. Settings afterwards shows: your name, who is on the list, 'Add a phone', 'Leave this list and delete my data', 'Export list' and the version.

**One-time developer setup:** Done once by you, about half a day in consoles plus the rules work: 1) Create a Firebase project on the free Spark plan. 2) Create the Firestore database in asia-south1 (Mumbai). The location cannot be changed later. 3) In Authentication, enable Anonymous sign-in. Leave 'automatic clean-up of anonymous accounts' OFF. 4) Register two Android apps: com.grocerysync.app, and com.grocerysync.app.qa (the qa build type adds '.qa'; build.gradle.kts line 78). Download google-services.json. Add the google-services Gradle plugin, the Firebase BoM (auth, firestore) and play-services-code-scanner. 5) Data model: households/{hid}; households/{hid}/members/{uid} {name}; invites/{code} {householdId, expiresAt}; households/{hid}/items/{docId} {name, type, value, unit, updatedAt, updatedBy, addedAt, deleted, serverUpdatedAt, lastChangeId}. docId must be a hash of the normalised name, because item names can contain '/', which Firestore IDs cannot. 6) Security rules: only members read or write a household. A member doc can be created only with a valid, unexpired invite for that household. Invites allow get but not list. Item fields are validated (name up to 100 chars, unit up to 16, amount 0-999999, name up to 40), mirroring Code.gs limits. Test the rules with the local Firestore emulator and deploy with the Firebase CLI. 7) Do not enforce App Check while builds are sideloaded, or allow unrecognized versions. 8) Publish a short privacy policy page (Play needs one anyway). The list itself needs no Cloud Functions (they would require the paid Blaze plan); change notifications need a sender, see *Offline and live updates*.

**Running cost:** Your family: $0. One household uses far less than 1% of the free daily quota. Per household (my estimate: 3 phones, 100 items, 50 changes a day, app open 20 times a day; the listener asks only for documents changed since the last sync; each change goes through a transaction): about 50 writes a day, or about 100 with an optional history document. Reads are about 170 a day: 50 transaction reads, about 100 fan-out reads to the other phones, and about 20 minimum charges, one per query on app open. The free tier (20K writes and 50K reads a day) covers about 200-400 households, with writes as the limit. After that, at us-central1 Blaze prices ($0.09 per 100K writes, $0.03 per 100K reads), it is about $0.003-0.004 per household per month, roughly $3-4 per 1,000 households. I could not confirm Mumbai prices. On Spark there is never a bill: Firestore stops serving when over quota. Daily quotas reset around midnight Pacific, about 13:30 IST in winter. On Blaze, budget alerts warn but do not cap spending.

**Privacy and data ownership:** The list contents (item names, amounts, units, display names, edit times) and anonymous user IDs are stored in your Firebase project in Mumbai, so the data stays in India. Google acts as the processor. You, the developer, can read every household's list in the console. Families no longer own the data in their own Drive, and they lose hand-editing in a spreadsheet and the History tab. Offer an in-app 'Export list' (CSV or WhatsApp text) and, optionally, a history subcollection. No email, phone number or Google account is collected. For a Play release, the Data safety form must declare what the Firebase SDKs collect (Google's own example is the Firebase installation ID as a 'Device or other ID') and the list as user content. Lock-in is high (proprietary API and rules), but the data model is tiny and the app keeps a remote-agnostic seam, so moving later is cheap.

**Offline and live updates:** Realtime: a Firestore snapshot listener runs while the app is in the foreground and replaces today's 5-second poll (LiveSync.POLL_INTERVAL_MS). Another phone's change arrives in about a second. Offline: keep the app's own SQLite mirror and outbox (GroceryDatabase, ListLogic.overlay, the pending/failed-change UI, SyncWorker) exactly as they are, and use Firestore only as the remote. Each outbox change is applied in a Firestore transaction that reproduces the Code.gs rules: the newest edit time wins (stale otherwise), a delete is a 'deleted' tombstone so an offline phone cannot bring the item back, Added At is written once, and the same change id is reported as a duplicate. Transactions fail offline. That is fine here: the change stays in the outbox and is sent later, which is what happens today. The alternative is to let Firestore's own persisted cache (on by default on Android, 100 MB) and its offline write queue replace the outbox. That means less code, but you would rebuild the pending/failed UI and lose 'stale' detection. Change notifications ([feature 7](feature-ideas.md#7-notification-when-someone-else-changes-the-list-and-an-im-going-shopping-alert)) are part of this move: they were taken out of 1.6, whose background check every 15 minutes at best could be hours late. The listener runs only while the app is open, so while it is closed Firebase Cloud Messaging (FCM) pushes a notification to the household's other phones when someone adds to To buy, with no polling. What that adds to the setup: 1) A sender, because the app must not hold FCM's server credentials. Either Cloud Functions on a Firestore trigger on the items, which need the Blaze plan (claim 7): pay as you go, with a billing account linked to the project, and budget alerts that warn but do not cap spending. Or a small Cloudflare Worker (the fallback's stack; its free limits are claim 19) that holds the credentials, which the writing phone calls after its change is saved, and which checks the caller's Firebase ID token and household membership before it sends; the project then stays on Spark. 2) In the app: firebase-messaging beside the google-services setup and the Firebase BoM, a messaging service and a notification channel, each phone's FCM token in its member document, and the POST_NOTIFICATIONS runtime permission on Android 13+, with a switch under Settings > This phone. 3) Not in the fact check, so check before deciding: what Cloud Functions cost on Blaze at the family's volume (whether it stays $0), and any FCM price or limit.

**Migration effort:** Medium-high: about 1-2 weeks for one developer (my estimate). 1) Extract a ListRemote interface from SheetsClient (list/apply returning the existing ListResult/ApplyResult) and add FirestoreRemote. SyncEngine's coalescing, push backoff and its data-safety rule (an op is deleted only after confirmation) stay. 2) SyncEngine and Protocol.kt: the protocol-version and 'script outdated' gating (Protocol.takesUnits, scriptOutdated) and the Apps Script and Google HTML-page error mapping no longer apply on the new path. 3) GroceryDatabase.commitPull replaces the whole mirror today. Add a merge for delta results (changed items and tombstones), plus meta rows for householdId and lastServerSync. 4) LiveSync: start and stop the listener with the foreground instead of the timer. Keep the loop for pushes and backoff. 5) Settings: remove Web app URL, Secret token, Paste setup code and Test connection (SettingsScreen, SettingsViewModel, SettingsStore, SetupCode, TokenEntry, TokenRedaction). Add a first-run Start/Join screen, Add a phone (QR, code, share), a members list, 'Leave this list and delete my data' and Export. 6) Update AppContainer and Gradle. 7) Tests: SyncEngine tests run against a fake ListRemote. UI tests that use FakeSheetServer move to that fake or to the Firestore emulator. Add tests for the security rules. 8) Retire Code.gs after the move. Existing data: one tap on the phone that has the Sheet reads the full list through the existing web app and uploads it with Updated At/By and Added At unchanged. The Sheet remains as an archive.

**Risks:** 1) Lock-in to Firebase's API and rules (mitigated by the ListRemote seam and Export). 2) A mistake in the security rules could expose a household's list or let strangers write to it. Test the rules in the emulator before any release. 3) Identity is per install. The app turns off Android backup (AndroidManifest allowBackup=false), so a reinstall or 'Clear data' creates a new anonymous user, who must rejoin with a code from another family phone. If the last phone of a household is reset, the list is unreachable. Add an optional 'Link Google account' (Credential Manager) before a public release. 4) Never enable anonymous auto clean-up: it deletes anonymous accounts 30 days after creation and would log out every phone. 5) When Spark is over quota, Firestore stops until the quota resets. Google's pages disagree on whether that lasts for the day or the rest of the month. 6) App Check with Play Integrity blocks sideloaded APKs unless unrecognized versions are allowed. 7) Rules cannot rate-limit code guessing. Keep codes 8 characters from an alphabet without look-alikes (about 10^12), short-lived and single-use. Auth's limit of 100 new accounts per IP per hour slows mass guessing. 8) Billing: a listener reattached after more than 30 minutes is billed like a new query, so always query 'changed since last sync', never the whole list. 9) Newest-wins depends on phone clocks. Reuse ServerClock's offset and cap times at server time in the transaction, as Code.gs does with effectiveTime_. 10) Play policy: Data safety declarations, and possibly the account-deletion rule (how anonymous sign-in is treated is unconfirmed). 11) The family loses hand-editing in the Sheet.

**Verdict:** RECOMMENDED. This is the only option that removes all user setup and also gives push-style live updates, India data residency, an official Android SDK, a free tier that covers your family indefinitely and a few hundred households, and no inactivity pause. Google runs the server and the sign-in, so the only security code you write is the rules.


### 2. Your own small server: Cloudflare Worker + D1 (SQLite) speaking today's list/apply protocol

**What users do:** For the family it looks the same as option 1. Phone A: install, tap 'Start a new list', type a name, then 'Add a phone' shows a QR code and an 8-character code (with the one-tap 'Bring my items from the Google Sheet' for your family). Phone B: install, tap 'Join a family list', scan or paste the code, type a name, and the list appears. No Google account, Sheet, URL or token. The one difference: 'live' still means the app checks every ~5 s while it is open (as today), unless you later add WebSockets.

**One-time developer setup:** 1) Create a free Cloudflare account and install the wrangler CLI. 2) Create a D1 database. Only an 'apac' location hint is available; there is no India option. 3) Write the Worker in TypeScript with these endpoints: POST /households (create, with optional initial items); POST /invites; POST /join {code, name}, which returns a random device secret (store only its hash); GET /list?since=; and POST /apply. The item rules are ported from Code.gs: normalizeKey_, applyUpsert_, applyDelete_, tombstones (30-day TTL), change-id dedupe, Added At and unit normalisation. 4) Build abuse protection yourself: limit join attempts per IP and per code, expire invites, and cap list and request size. 5) Deploy to a workers.dev subdomain or your own domain and put the base URL in the app. 6) Set up backups/export and monitoring. Running this is permanently your job.

**Running cost:** Your family: $0. Per household (my estimate: 3 phones, app open about 40 min a day, 5 s polling): about 480 polls + 50 applies + 20 opens = about 550 requests a day. Workers Free (100K requests a day) fits about 180 households, or about 430 with 15 s polling. D1: Code.gs's 'since' today re-reads and MD5-hashes the whole list on every poll (revisionOf_). In the port, keep a per-household revision counter so an unchanged poll reads 1 row. That gives about 5-6K rows read and about 200 rows written per household per day, and D1 Free (5M reads and 100K writes a day) fits about 500 households on writes. Paid: $5 a month minimum covers 10M requests a month (about 600 households), then $0.30 per million, about $0.005 per extra household per month. Over the free caps, requests and queries fail until 00:00 UTC (05:30 IST).

**Privacy and data ownership:** The data sits in your Cloudflare account, and you design the schema and can read everything. You cannot keep it in India: D1 offers only a location hint, and its jurisdictions are EU, US and FedRAMP. Third-party sources say India's DPDP Act currently allows the transfer; I did not check that against the official gazette. Lock-in is the lowest of all options: plain JavaScript plus SQLite, movable to any server. For a Play release, the same Data safety duties apply (the device secret is an app-generated identifier).

**Offline and live updates:** Offline: unchanged. The app's SQLite mirror, outbox, coalescing and WorkManager push stay exactly as they are. Realtime: polling every 5 s while the app is open, as today. Later, a Durable Object per household could push over a WebSocket (outgoing messages are free and incoming ones are billed at 20:1), but I could not pin down the free plan's duration limits.

**Migration effort:** Medium overall: the most server work but the fewest app changes, about 1 week (my estimate). App: SheetsClient keeps its OkHttp code and the protocol-3 list/apply JSON contract. Its base URL becomes a constant, and the token becomes the device secret from /join. Protocol.kt's handling of Apps Script and Google HTML pages shrinks to plain HTTP errors. SyncEngine, LiveSync, GroceryDatabase, ListLogic and most FakeSheetServer-based unit and UI tests stay as they are, because the JSON contract is the same. Settings changes as in option 1: URL, token and setup code go out; Start/Join and Add a phone come in. Server: port the item rules from Code.gs. The file has about 2,350 lines, but most of it is sheet layout, the onEdit hand-edit trigger and Sheets error handling, all of which disappear. Existing data moves with the same one-tap import: pull from the Sheet with the saved URL and token, then POST to /households.

**Risks:** 1) You become the operator: authentication, invite brute-force protection, rate limiting, backups, uptime and abuse handling are yours, and one bug can expose every family's list. 2) The free-plan caps are hard limits: errors until 00:00 UTC. 3) No data residency in India. 4) Polling costs requests and battery compared with push. 5) No official mobile SDK, so offline and realtime rely only on what the app already does (which is a lot).

**Verdict:** FALLBACK. Choose this if you would rather keep the sync protocol and engine you have already tested, avoid Google lock-in, or find Firestore's transaction/rules design awkward. Users get the same zero-setup experience, but you run and secure a small public server.


### 3. Google-native: the app signs in with Google, creates the Sheet itself and shares it (drive.file scope, no Apps Script)

**What users do:** Phone A: 1) Install the app. 2) Tap 'Continue with Google' and pick the account. 3) Approve access to 'only the files used with this app'. Without brand verification, the consent screen does not show your app's name or logo. 4) The app creates a 'Kirana List' Sheet in A's Drive. 5) Tap 'Add a phone' and type B's Gmail address. The app shares the Sheet (Google emails B) and shows a link or QR code containing the file ID. Phone B: 1) Install the app. 2) Tap 'Continue with Google'. 3) Open the link or scan the QR code. Google's file picker opens in the browser, showing only that file. 4) Tap the file, and the list appears. Both people need a Google account. It comes to about 3 taps plus an email address on A and about 4 taps on B. Not confirmed: whether a 'Shared with me' file appears in the picker when filtered by file ID, and whether B's access survives reinstalling the app.

**One-time developer setup:** 1) Create a Google Cloud project and enable the Drive and Sheets APIs. 2) Fill in the OAuth branding. 3) Create Android OAuth clients for each package and signing key: release, debug, and qa (com.grocerysync.app.qa). 4) Set the publishing status to 'In production' with only drive.file, openid, email and profile. Left in 'Testing', both phones must re-approve every 7 days, and you maintain a list of up to 100 test users. 5) Brand verification is optional; it needs a verified domain, a home page and a privacy policy.

**Running cost:** $0 for everyone, with no server. The Sheets API is free within quota: 300 reads a minute per project, shared by all users, and 60 per user. Polling every 5 s means 12 reads a minute per phone, so only about 25 phones across all households can poll at the same time. Cheaper polling: check the Drive file's modified time or version and read the Sheet only when it changed (how quickly that signal updates is unconfirmed). Google says it plans to charge for usage over quota 'later in 2026'; I could not confirm the details.

**Privacy and data ownership:** Best ownership of all the options: the list stays in the family's own Google Drive and stays hand-editable, and you, the developer, never see it because there is no server. It does require Google accounts and typing a Gmail address. If A deletes the file or removes the app's access, B loses the list.

**Offline and live updates:** Offline: today's outbox stays. Realtime: polling only, because push needs a server with Pub/Sub or webhooks plus FCM. The server-side lock, change-id dedupe and merge in Code.gs disappear. Two phones writing through the Sheets API at the same moment can overwrite each other (simultaneous appends have been reported to collide), so the app needs its own conflict scheme, such as a change-log tab per phone. That scheme is untested.

**Migration effort:** High. Add Credential Manager sign-in, the Android Authorization API (drive.file) and the new Drive picker flow, plus a Sheets/Drive REST client. Move the Code.gs rules (tombstones, newest-wins, Added At, units, sheet layout) into the app, and solve concurrency without a lock. The onEdit stamping of hand edits is lost. Settings becomes sign-in, share-by-email and the picker. Data: phone A could pick the family's existing Sheet in the picker and keep using it, since its layout is already right, or the app copies the items into a new Sheet.

**Risks:** 1) Not zero setup: Google sign-in, consent, the picker and an email address. 2) A consent screen without your app name may worry relatives. 3) Without the server lock, simultaneous edits risk data loss. 4) The project-wide Sheets quota blocks public scale. 5) New Drive picker rules are reportedly enforced from 16 Nov 2026; that date comes from a third-party copy, not Google. 6) Switching to the broader 'spreadsheets' scope triggers sensitive-scope review, or the unverified-app warning with a 100-user cap.

**Verdict:** NOT RECOMMENDED as the main path. It removes Apps Script and tokens but keeps Google sign-in and picker steps, gives up Code.gs's server-side safety, and cannot scale. Consider it only if 'the list must live in each family's own Drive' is a hard requirement.


### 4. Supabase: Postgres + anonymous Auth + Realtime (Mumbai region)

**What users do:** Identical to option 1: Start or Join, type a name, Add a phone with a QR code and 8-character code, then the other phone scans it and types a name. The difference: on the Free plan the project pauses after a week with no activity. Every phone then shows 'offline' until you unpause it by hand in the dashboard.

**One-time developer setup:** 1) Create a Supabase project in ap-south-1 (Mumbai). 2) Enable anonymous sign-ins and add CAPTCHA/Turnstile (recommended). 3) Create households, members, invites, items and tombstones tables with row-level security. 4) Write a join_household(code) RPC and an apply_changes RPC that port the Code.gs rules to SQL/PLpgSQL. 5) Raise the 30-sign-ins-per-hour-per-IP limit. 6) Add supabase-kt, which is community-maintained, not official.

**Running cost:** $0 for your family, except for the pause risk. Free tier: 500 MB database, 5 GB egress, 50K MAU, 200 realtime connections and 2M realtime messages a month. At about 150 realtime messages per household per day, that is about 400 households. Pro costs $25 a month (5M messages, 500 connections, 100K MAU).

**Privacy and data ownership:** Data stays in Mumbai in standard Postgres. Lock-in is low and the stack can be self-hosted. You, the developer, can read all data.

**Offline and live updates:** Realtime comes through supabase-kt (Postgres Changes, or Broadcast for scale). There is no offline cache, so the app's existing outbox stays, which is fine because it already exists.

**Migration effort:** Medium-high: similar to option 1, plus SQL RPCs and a community SDK with its Ktor dependencies. Settings and the data import work as in option 1.

**Risks:** 1) Free projects pause after 1 week of inactivity, so a family holiday breaks the app. 2) The Kotlin SDK is community-maintained. 3) The anonymous sign-in rate limit may hit Indian carrier CGNAT (my inference). 4) Cost jumps from $0 to $25 a month. 5) Unconfirmed whether anonymous users count as MAU.

**Verdict:** THIRD CHOICE. Good technology with an India region, but the inactivity pause on Free is a bad fit for a few households. Reconsider it only if you would pay $25 a month from day one.

## Migration plan

1. Prepare (no code): on both phones, make sure Settings shows no pending or failed changes. Make a copy of the Google Sheet (File > Make a copy, or download .xlsx) as a backup. Leave the Apps Script web app deployed.
2. Firebase setup: create the Spark project, create the Firestore database in asia-south1 (cannot be changed later), enable Anonymous sign-in with auto clean-up OFF, and register com.grocerysync.app and com.grocerysync.app.qa. Write the security rules and test them in the local Firestore emulator before deploying. Choose the sender for change notifications: Cloud Functions need the project on Blaze (a billing account, plus a budget alert), the Worker keeps it on Spark; check the costs first (see *Offline and live updates* in option 1).
3. Refactor without behaviour change (release 1.3.x, optional): extract a ListRemote interface from SheetsClient (list/apply returning ListResult/ApplyResult) and make SyncEngine depend on it. Move the SyncEngine tests onto a fake ListRemote. Run the existing unit and UI tests; nothing should change for users.
4. Build 1.4: FirestoreRemote (transactional apply that copies Code.gs's newest-wins, tombstone, Added At and dedupe rules; delta listener on serverUpdatedAt > lastSync); a merge in GroceryDatabase (in place of the full mirror replace in commitPull); LiveSync driving the listener in the foreground; first-run Start/Join screen; Add a phone (QR code, 8-character code, WhatsApp share, Google code scanner to join); members list; 'Leave this list and delete my data'; Export list; change notifications through FCM (each phone's FCM token in its member document, the sender on the items' Firestore trigger or in the Worker, a notification channel, POST_NOTIFICATIONS on Android 13+ and a switch under Settings > This phone). Keep SheetsClient, SettingsStore's URL/token and SetupCode only for the one-time import.
5. One-tap import of the family's current list, on the phone that has the Sheet: 1.4 shows 'Move this list off Google Sheets'. On tap it (a) pushes that phone's outbox to the Sheet one last time through the existing SyncEngine; (b) reads the full list from the web app (SheetsClient.list with since = null); (c) creates the household and writes every item (Batti, Dahi, Diya, Kishmish, Oil, ...) with name, type, amount, unit, Updated At, Updated By and Added At unchanged, in batched writes, so 'Added by'/'Updated by' and the times stay correct; (d) switches this phone to Firestore and erases the saved URL and token from SettingsStore; (e) shows the Add-a-phone QR code and code.
6. Second phone: after updating to 1.4, it sees 'This list has moved. Join with the code from the other phone'. Scan or paste the code and keep the same name, so 'Added by <name>' stays consistent. Before switching, it sends any changes still in its outbox to Firestore with their original times; newest-wins keeps the latest edit, as today. Then it erases its URL and token too.
7. Rehearse first with the qa build (com.grocerysync.app.qa) on the emulator, using a copy of the Sheet and a test household. Then do the real move on both phones the same day. Ship 1.4 through the same channel and signing key as 1.3 (the release APK), so it installs over 1.3 and keeps the local list and outbox.
8. Keep the Apps Script deployment running read-only for about 2 weeks as a safety net. Then archive the deployment (Deploy > Manage deployments) and keep the Sheet as an archive. Do not delete it.
9. Release 1.5: delete the Sheets path (SheetsClient's Apps Script handling, the Apps Script page parsing in Protocol.kt, SetupCode, TokenEntry, TokenRedaction, the URL/token fields), retire Code.gs and rewrite the README for the new setup ('install, Start or Join, type your name').
10. Later, before any public release: optional 'Link Google account' (Credential Manager) for recovery, an optional history subcollection, a privacy policy page, and the Play Data safety answers for the Firebase SDKs.

## Installing the app

### For the family now

Right now, in India: keep sideloading the signed release APK, including for 1.4, the migration release. Nothing has changed for sideloaded installs in India yet, adb installs never need verification, and using the same key means 1.4 installs over 1.3 and keeps each phone's local list and pending changes. Least effort over time: once both phones are on the new backend, open a Play Console personal account (US$25 one-time; government ID, card and phone checks). Create the app, and before any open-testing or production release use Play App Signing > 'Change key' to give Play a copy of your existing release key, so Play builds update the sideloaded app in place. Upload AABs to the internal testing track and add the family's Gmail addresses to a tester list. Each phone opens the opt-in link once and installs from Play; after that, updates arrive automatically within minutes of upload. Internal-only apps need no Data safety form and no 12-tester test, and Play App Signing registers the app for developer verification automatically. If you skip 'Change key', each phone must uninstall the sideloaded copy once. Do that only after the move to Firestore, so nothing is lost except a rejoin with a code. Zero-cost alternative: keep sideloading, and before Google's 2027 global rollout reaches India, open the free limited distribution account (no ID), register com.grocerysync.app with your existing key and authorise each phone. Google's pages say up to 20 devices in one place and 50 in another. Updates stay manual.

### For a public release

Use the same Play Console personal account. 1) Build an AAB with Play App Signing. targetSdk 36 already meets the API-36 rule for new apps. 2) Publish a public privacy policy page and link it both in Play Console and inside the app. 3) Fill in the Data safety form, declaring Firebase SDK data (e.g. Firebase installation ID / anonymous user ID as 'Device or other IDs') and the list contents and display names as user content, encrypted in transit. 4) Complete content rating, target audience and ads declarations. 5) Ship in-app 'Leave this list and delete my data' plus a web page or form for deletion requests. How Play treats anonymous sign-in under the account-deletion rule is unconfirmed, so do both. 6) Run a closed test with at least 12 testers opted in for 14 consecutive days; recruit 15 or more so one dropout does not restart the clock. Internal testers do not count. 7) Apply for production; Google says review usually takes 7 days or less. Plan on about 3-4 weeks from account creation (my estimate). Before going public, add 'Link Google account' for recovery, plan for more than about 200-400 households (Blaze with budget alerts, which do not cap spending), and keep App Check off or permissive for any sideloaded builds.

- Play Console personal account: US$25 one-time; government ID and card in your legal name; contact email and phone verified; new personal accounts must also verify a real Android device through the Play Console app before publishing.
- Personal accounts created after 13 Nov 2023 need a closed test with at least 12 testers opted in for 14 consecutive days before applying for production; internal testing does not count; production review usually takes 7 days or less.
- Internal testing track: up to 100 testers per app, added by email list and joining through an opt-in link; builds reach testers within minutes; internal tests 'might not be' reviewed; apps only on internal testing do not need the Data safety form.
- New Play apps must be uploaded as AABs with Play App Signing; the app signing key, including switching to your own existing key, can be changed only before a release reaches open testing or production.
- Since 31 Aug 2026, new apps and updates must target API 36; this project already targets 36 (android/app/build.gradle.kts).
- Android developer verification: enforcement began 30 Sep 2026, only for installs from participating stores in Brazil, Indonesia, Singapore and Thailand; sideloads are not affected yet; global rollout is in 2027. I found no India date (not confirmed).
- ADB installs never need verification, and the advanced flow's 24-hour wait does not apply to ADB. Once enforcement applies, unregistered apps install or update only with the advanced flow enabled or via ADB.
- Apps on Play that use Play App Signing are registered for developer verification automatically.
- Limited distribution account: free and needs no government ID; meant for personal use and testing on a fixed list of devices. The FAQ says up to 20 devices, other Google pages say 50. The FAQ says it can later move to a full account; another help page disagrees.
- Firebase App Distribution is free, but updates are not automatic, and Google says it will also need verification once enforcement applies; Play internal testing is the lower-effort family channel.
- Code facts: the app has allowBackup=false and device-transfer exclusion, so any new anonymous identity is lost on reinstall (rejoin by code is required); the qa build type uses applicationId com.grocerysync.app.qa, which needs its own Firebase app registration.
